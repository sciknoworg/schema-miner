Workflow Description

schema-minerpro progresses through four stages, moving from a process specification to a refined, ontology-grounded scientific schema. Each stage has a defined input, output, and validation signal so that experts can inspect and guide the workflow.

Shared workflow variables

  1. LLM_PROVIDER and LLM_MODEL select the inference backend and model.
  2. PROCESS_NAME and PROCESS_DESCRIPTION initialize the scientific process being mined.

These four input variables apply to every stage of the workflow. They are part of what makes schema-miner plug-and-play over LLM providers and scientific processes. The normal starting point is to declare these variables in the project-level .env file.

Stage 1

Initial Schema Mining

Generate a first JSON schema from a process specification document.

Example: ALD specifications produce top-level fields for reactants, process conditions, film properties, safety, and stability.

Configuration examples

.env entries: the usual configuration for a single process run.

PROCESS_NAME = [name the process]
PROCESS_DESCRIPTION = [short 2 or 3 sentence description of the process]
STAGE1_SPECS_PATH = [path to the process specification file]
RESULTS_PATH = [path where the output schema and log will be stored]

Python or batch override: for many processes, a script can read data/stage1/process.txt and set PROCESS_NAME and PROCESS_DESCRIPTION before invoking the same command.

Stage input variables
  • STAGE1_SPECS_PATH points to the expert-written process specification used to start schema mining, for example data/stage1/process-description.pdf.
  • For batch runs over many processes, data/stage1/process.txt can initialize PROCESS_NAME and PROCESS_DESCRIPTION before each run.
Output path
RESULTS_PATH points to the directory where data/stage1/schema/[model-name].json and data/stage1/schema/stage1.log are written; for example, data/stage1/schema/qwen3-30b-a3b-instruct-2507.json.
CLI tags
--stage 1.
Command line usage scenarios
schema-miner --stage 1
Expert feedback
data/stage1/feedback/[model-name].txt stores expert feedback used as input to Stage 2.

Stage 2

Preliminary Refinement

Refine the initial schema using a small expert-curated scientific corpus.

Example: Feedback can request missing units, merge duplicate properties, or reorganize nested process fields.

Stage input variables
  • STAGE2_PAPERS_PATH points to the curated seed-paper directory, for example data/stage2/batch1 with papers such as Bairagya_2024.pdf and Browne_2013.pdf. Use a curated seed set of about 10 full-text papers that a domain expert has personally checked for quality and relevance. This seed set extends the initial process specification from Stage 1 into a richer schema with additional process parameters and conditions.
  • The first paper starts from the Stage 1 schema supplied with --schema, for example data/stage1/schema/qwen3-30b-a3b-instruct-2507.json.
  • Optional --expert-feedback <text or path> can provide inline feedback or a file such as data/stage1/feedback/[model-name].txt.
Output path
RESULTS_PATH points to the Stage 2 batch output directory, where data/stage2/schema-batchN/[model-name].json, data/stage2/schema-batchN/stage2-batchN.log, and intermediate schemas under data/stage2/schema-batchN/intermediate-schema/[model-name]/ are written.
CLI tags
  • --stage 2, --schema, optional --expert-feedback, and optional --papers.
  • --papers N controls how many papers are processed per batch; omitting it processes one paper per batch. For example, if Stage 2 has 10 papers and the user runs --papers 2, schema-miner creates five batches and asks for updated expert feedback after each batch. With --papers all, all available papers are processed together in one run, reusing the expert feedback provided at the beginning without reprompting between papers.
Command line usage scenarios

Default: process one paper per batch.

schema-miner --stage 2 \
    --schema data/stage1/schema/qwen3-30b-a3b-instruct-2507.json

Add expert feedback directly on the command line.

schema-miner --stage 2 \
    --schema data/stage1/schema/qwen3-30b-a3b-instruct-2507.json \
    --expert-feedback "Please add units for all temperature and pressure fields."

Read expert feedback from a file and process all available papers in one run.

schema-miner --stage 2 \
    --schema data/stage1/schema/qwen3-30b-a3b-instruct-2507.json \
    --expert-feedback data/stage1/feedback/qwen3-30b-a3b-instruct-2507.txt \
    --papers all

Choose an explicit paper batch size.

schema-miner --stage 2 \
    --schema data/stage1/schema/qwen3-30b-a3b-instruct-2507.json \
    --papers 2
Expert feedback
data/stage2/feedback-batchN/[model-name].txt records expert feedback for the next Stage 2 batch or the Stage 3 starting point; for example, data/stage2/feedback-batch1/qwen3-30b-a3b-instruct-2507.txt.

Stage 3

Final Refinement

Generalize and validate the schema against a larger, non-curated corpus.

Example: Stage 3 separates ALD growth behavior fields such as growth per cycle and nucleation period.

Stage input variables
  • STAGE3_PAPERS_PATH points to the extended-corpus directory, for example data/stage3/batch1 with papers such as 1-s2.0-S0022286025034994-main.pdf. Use an extended corpus of about 50-70 additional full-text papers from bibliographic sources such as journal sites, themed databases, or Google Scholar. The papers do not all need full manual quality review, but titles should at least be checked for process relevance and for experimental or simulation parameters.
  • The first Stage 3 paper starts from the refined Stage 2 schema supplied with --schema, for example data/stage2/schema-batch2/qwen3-30b-a3b-instruct-2507.json.
  • Optional --expert-feedback <text or path> can provide inline feedback or a file such as data/stage2/feedback-batch2/[model-name].txt.
Output path
RESULTS_PATH points to the Stage 3 batch output directory, where data/stage3/schema-batchN/[model-name].json, data/stage3/schema-batchN/stage3-batchN.log, and intermediate schemas under data/stage3/schema-batchN/intermediate-schema/[model-name]/ are written.
CLI tags
  • --stage 3, --schema, optional --expert-feedback, and optional --papers.
  • --papers N again controls the batch size. For example, --papers 3 processes three papers at a time, writes an updated schema for that batch, and then expects the feedback file to be reviewed before the next batch continues refinement. With --papers all, the extended-corpus papers are processed together and the initial expert feedback is reused throughout that run without reprompting.
Command line usage scenarios

Default: process one paper per batch.

schema-miner --stage 3 \
    --schema data/stage2/schema-batch2/qwen3-30b-a3b-instruct-2507.json

Add expert feedback directly on the command line.

schema-miner --stage 3 \
    --schema data/stage2/schema-batch2/qwen3-30b-a3b-instruct-2507.json \
    --expert-feedback "Ensure all quantities reference standard SI units."

Read expert feedback from a file and process the extended corpus in one run.

schema-miner --stage 3 \
    --schema data/stage2/schema-batch2/qwen3-30b-a3b-instruct-2507.json \
    --expert-feedback data/stage2/feedback-batch2/qwen3-30b-a3b-instruct-2507.txt \
    --papers all

Choose an explicit paper batch size.

schema-miner --stage 3 \
    --schema data/stage2/schema-batch2/qwen3-30b-a3b-instruct-2507.json \
    --papers 3
Expert feedback
data/stage3/feedback-batchN/[model-name].txt is used when another refinement batch follows; the final Stage 3 schema is the input to ontology grounding.

Stage 4

Ontology Grounding

Ground schema properties to formal ontology concepts and units.

Example: Temperature maps to a QUDT temperature quantity kind, while dosing time may be revised to domain-preferred units.

Stage input variables
  • The final refined schema is supplied with --schema, for example data/stage3/schema-batch2/qwen3-30b-a3b-instruct-2507.json.
  • --ontology-grounding selects prompt or agentic grounding.
  • Shared .env variables such as LLM_PROVIDER, LLM_MODEL, PROCESS_NAME, and PROCESS_DESCRIPTION provide the model and process context.
Output path
RESULTS_PATH points to the directory where ontology-aligned JSON is written, typically as [schema-name]-with-qudt.json; reference outputs include results/Ideal Schema/Atomic-Layer-Deposition/*-with-qudt.json and results/Ideal Schema/Atomic-Layer-Etching/*-with-qudt.json.
CLI tags
--ontology-grounding prompt or --ontology-grounding agentic, plus --schema.
Command line usage scenarios

Prompt-based grounding.

schema-miner --ontology-grounding prompt \
    --schema data/stage3/schema-batch2/qwen3-30b-a3b-instruct-2507.json

Agentic grounding with ontology lookup and semantic search.

schema-miner --ontology-grounding agentic \
    --schema data/stage3/schema-batch2/qwen3-30b-a3b-instruct-2507.json
Validation
Expert review verifies lexical matches, FAISS semantic matches, QUDT quantity kinds, units, URI metadata, and any LLM-assisted grounding decisions.

Configuration Reference

.env file variables

View .env.example

The CLI reads a project-level .env file before each command. Keep the provider and process variables stable, then update only the stage path and output path for the stage being run. 

# -- Active LLM Provider --
LLM_PROVIDER = 'SAIA'
LLM_MODEL = 'qwen3-30b-a3b-instruct-2507'
SAIA_API_KEY = 'Your API key'
SAIA_BASE_URL = 'https://chat-ai.academiccloud.de/v1'

# -- Process Configuration --
PROCESS_NAME = 'Atomic Layer Deposition'
PROCESS_DESCRIPTION = 'ALD experimental schema mining workflow'

# -- Data Path Configuration --
STAGE1_SPECS_PATH = 'data/stage1/process-description.pdf'
STAGE2_PAPERS_PATH = 'data/stage2/batch1'
STAGE3_PAPERS_PATH = 'data/stage3/batch1'

# -- Output Path Configuration --
RESULTS_PATH = 'data/stage1/schema'
Provider
Use OPENAI_API_KEY for OpenAI, SAIA_API_KEY/SAIA_BASE_URL for KISSKI SAIA or OpenRouter, or HuggingFace_Access_Token with HUGGINGFACE_USE_LOCAL for Hugging Face GPU runs.
Stage 1
STAGE1_SPECS_PATH points to the process specification; RESULTS_PATH points to the Stage 1 schema directory.
Stage 2
STAGE2_PAPERS_PATH points to a curated batch such as data/stage2/batch1; update RESULTS_PATH to the matching schema batch output directory.
Stage 3
STAGE3_PAPERS_PATH points to a broader-corpus batch such as data/stage3/batch1; update RESULTS_PATH to the matching Stage 3 output directory.
Grounding
Ontology grounding uses the final schema passed with --schema and writes grounded output under RESULTS_PATH.

Results Snapshot

The evaluation compares schemas generated by GPT-4o, GPT-4-turbo, and LLaMA 3.1 (8B) across refinement stages. Quantitative metrics capture schema variance, while qualitative review identifies model stability and grounding quality.

Representative Stage 3 Experimental Schema Similarity
Use case Model pair ROUGE-L BERT-F1
ALD GPT-4o vs GPT-4-turbo 0.3690 0.8046
ALE GPT-4o vs GPT-4-turbo 0.3552 0.7631

Primary quantitative metrics: ROUGE-L, BLEU, and BERTScore. See the paper for the complete cross-stage matrices.

Qualitative Findings

For ALD, GPT-4o and LLaMA 3.1 (8B) maintained the most coherent schema structures across refinement stages. For ALE, GPT-4o and GPT-4-turbo were the most reliable at capturing the process structure. The hybrid grounding strategy reduced unnecessary LLM calls by using direct ontology lookups before semantic search.
